# FP8 x MXFP4 Fused-Gather Matmul Optimization

## Rationale

Optimize `python/triton_kernels/triton_kernels/matmul.py` for the GB300 target workload that uses fp8 activations, mxfp4 weights, and fused gather. This workstream needs durable notes because the tuning loop will span multiple sessions, require direct measurement on this machine, and be handed back and forth between the user's laptop and this checkout.

## Invariants

- Keep the public `triton_kernels.matmul` behavior stable unless we explicitly agree to an API change.
- Preserve correctness for the target fp8 x mxfp4 fused-gather cases before trading for speed.
- Record benchmark conditions, observations, and performance deltas in persistent memory outside the repo so multi-week tuning stays reproducible.
- Preserve handoff clarity: the user syncs work by pushing into and fetching from this machine's repo; there is no access to the user's laptop.

## Current Understanding

The current dispatch path is `python/triton_kernels/triton_kernels/matmul.py`, which canonicalizes inputs, decides whether TMA/persistent execution is legal, computes `opt_flags`, and launches either `_matmul` or `_p_matmul`. For the target workload on Blackwell-class GPUs, the persistent kernel path is the likely focus because it already supports TMA-based operand handling and the heuristics bias toward persistent execution for low-precision LHS inputs.

The exact workload shape family is now grounded by `/root/code/openai/lib/ki/tests/spo/test_matmul_parrot_gather.py`, which the user identified as a direct description of the target `triton_kernels.matmul` inputs. The primary non-parrot cases use:

- `n_expts_act = 4`
- `b_shape = (5120, 10240)` meaning `K = 5120`, `N = 10240`
- `batch_size` sweep from `1` up to `33792`
- `n_expts_tot` / `n_expts_shards` combinations: `(256, 8)`, `(256, 16)`, `(256, 32)`, `(272, 8)`, `(288, 8)`
- `is_parrot_gather = False`

The smaller parrot-gather case uses:

- `n_expts_act = 4`
- `b_shape = (1280, 2560)` meaning `K = 1280`, `N = 2560`
- `batch_size` sweep from `1` to `128`
- `n_expts_tot = 64`, `n_expts_shards = 1`
- `is_parrot_gather = True`

The KI test also fixes the exact datatype/config pattern we should optimize first:

- Activations: plain `torch.float8_e4m3fn`, not microscaled activations
- Weights: local-expert MXFP4 packed values plus MX scales in the default mxfp4 weight/value layouts
- Bias: `float32`
- Output: `torch.float8_e4m3fn`
- Fused activation: `swiglu` with `reduction_n = 2`
- Gathered/ragged dispatch: output rows scale with `batch_size * n_expts_act`
- Precision config: flexpoint output path with `flexpoint_saturate_inf=True`, per-run `x_scale`, expected `y_scale`, and `b_mx_scale`

The persistent kernel in `python/triton_kernels/triton_kernels/matmul_details/_p_matmul.py` already contains a fused-gather path:

- `HAS_GATHER = GatherIndx is not None`
- `USE_GATHER_TMA = HAS_GATHER and X_TMA_MODE == "dense"`
- `x = X.gather(offs_x_m, off_k_x // block_div)` when gather uses dense TMA

The non-persistent kernel in `python/triton_kernels/triton_kernels/matmul_details/_matmul.py` handles gather by loading row indices directly from `GatherIndx`, so it is a fallback/reference path but not the obvious Blackwell optimization target.

The test surface in `python/triton_kernels/tests/test_matmul.py` already exercises gather/scatter and fp8/mxfp4 cases together, but it also documents current guardrails that matter for planning:

- Gather is not supported in batched mode.
- Gathered activations currently do not combine with x-scale swizzling (`a_hbm_swizzling`) in tests.
- Blackwell/native MXFP heuristics in `opt_flags.py` and `opt_flags_nvidia.py` push many MXFP cases toward persistent/TMA execution and cap `block_k` to conserve shared memory.

Current exact-math tuning is centered on the perf-side sandbox kernel in `python/perf/matmul_ws_optimized.py`, not on the production `triton_kernels.matmul` path yet. The active sandbox baseline keeps `x_num_bufs=5` and `w_num_bufs=4`, then uses a helper-assisted row-fragment epilogue (`epilogue_row_subtile_factor=8`, `epilogue_schedule=wavefront`, `epilogue_store_helper=True`, `store_helper_warps=2`) plus packed `f32x2` math, a packed `b32` FP8 store path, `load_activation_regs=112`, and `store_helper_regs=16`.

That sandbox kernel is now implemented canonically in `python/examples/gluon/05-moe-bmm1-fused-gather.py` and re-exported through `python/perf/matmul_ws_optimized.py` as a thin compatibility shim for the benchmark harness. The example is intentionally standalone: after a brief experiment with a shared `_pipeline_utils.py` module, both `01-attention-forward.py` and the moved matmul example were restored to owning their own helper surface because the coupling added cleanup churn without enough payoff. The later matmul-side channel refactor was also rolled back, so the canonical example is back on the original manual ring/barrier pipeline shape rather than the `Channel(...)` abstraction.

The live tree now keeps only the promoted helper-wavefront kernel in `python/examples/gluon/05-moe-bmm1-fused-gather.py` and the single `python/perf/matmul_ws_optimized.py` shim that re-exports it. The separate async-TMA-store and direct-`gl.store` comparison kernels were useful experiments, but they did not beat the helper baseline on the target bucket, so they were removed from the canonical example and benchmark harness during cleanup. Their measurements and SASS/NCU learnings are still retained in the execution log below for future resurrection if the design direction changes.

The current cleanup pass also reduced the live example's internal scaffolding without changing the promoted helper-wavefront schedule. The now-fixed scheduling surface (`XCD_SWIZZLE=1`, `N_MAJOR=False`) has been removed from the live path, barrier allocation/invalidation is funneled through tiny ring helpers, the epilogue's repeated accumulator+bias load sequence is factored into one helper, and the Python wrapper now targets the single surviving kernel directly instead of carrying a pseudo-generic `_matmul_impl(...)` surface. The target bucket stayed flat-to-slightly-better after that refactor (`ws_optimized=0.3481 ms`, `gluon_optimized=0.3483 ms`, exact validation).

After a later cosmetic sync from the user, the live example now uses public-style helper names without leading underscores. The benchmark-facing shim continues to export `ws_matmul_kernel_optimized` for compatibility, but it now points at the cosmetically renamed `ws_matmul_kernel` symbol from the example. The target bucket stayed flat after the rename-only pass (`ws_optimized=0.3486 ms`, `gluon_optimized=0.3486 ms`, exact validation).

The current WS helper-wavefront kernel still uses a single accumulator buffer in TMEM. A direct experiment changing only `acc_num_bufs` from `1` to `2` in `ws_optimized` is not legal at the current `BLOCK_N x BLOCK_M = 256 x 128` accumulator tile: launch metadata reports TMEM use rising to `524` against a hardware limit of `512`. So future accumulator double-buffering work needs a tile/TMEM rebudget or a different accumulator ownership scheme, not just a larger `acc_num_bufs`.

The latest low-batch occupancy experiment says the current WS example should not trade away load buffering just to reach the half-SMEM / half-TMEM thresholds for 2 CTAs per SM. Temporary sweeps over reduced `X_NUM_BUFS` / `W_NUM_BUFS` combinations in the `BLOCK_M=16`, `32`, and `64` regimes did find under-half dynamic-SMEM points, but every candidate slowed down materially, and the follow-on experiment that doubled the persistent CTA count (`NUM_SMS` / launch grid) slowed them down again. Representative results were `batch=128` default `0.03432 ms` versus the mildest under-half candidate `x=4,w=3` at `0.03671 ms` and `0.03955 ms` with a virtual `2x` CTA count; `batch=384` default `0.03586 ms` versus `x=2,w=3` at `0.04326 ms` / `0.04628 ms`; and `batch=1024` default `0.04041 ms` versus `x=4,w=2` at `0.05507 ms` / `0.05952 ms`. NCU then confirmed that the doubled-grid run never actually achieved 2 CTAs per SM: for the `batch=128`, `x=4,w=3`, `sms_factor=2` case, `sm__ctas_active.avg.per_cycle_active` stayed at `1.00`, `Block Limit Registers` stayed `1`, and `Block Limit Shared Mem` stayed `1`. The key catch is that the candidate only falls under half if you count dynamic SMEM alone; once NCU's driver-side shared memory (`1.02 KiB`) is included, the total per block is still above half an SM, and `128` registers/thread would have blocked 2-CTA residency anyway. The durable note for that pass is `.codex/initiatives/artifacts/ws-buffer-count-occupancy-exp-2026-04-10.md`.

Correctness for exact-math epilogue work can no longer treat `original` as the oracle. `python/triton_kernels/triton_kernels/swiglu_details/_swiglu.py` computes SwiGLU through `exp_ftz`, which lowers to `ex2.approx.ftz.f32`, so `original` is an approximate fused-activation reference. The benchmark harness now has an exact host-side validation mode built from `matmul_torch` + exact `torch.sigmoid` + flexpoint-style requantization, and exact `ws_optimized` work should validate with `--validation-reference exact`.

There is now also a durable SASS note for the current helper-store and async-TMA-store epilogues at `.codex/initiatives/artifacts/ws-epilogue-store-overlap-sass-2026-04-09.md`. The important conclusions are: the fragment epilogue is already software-pipelined in source; ptxas further interleaves the producer-side ring writes and the epilogue-owned async-TMA-store issue path with ongoing SwiGLU arithmetic; and the helper-store design still wins mainly because the final global-store work lives on separate warps. A follow-up helper tweak that releases the SMEM ring slot immediately after the helper partition loads the fragment into registers is legal, changes the helper-consumer SASS as intended (`arrive(empty)` moves ahead of the `STG.E` cluster), and improves the target bucket slightly (`0.3481 -> 0.3474 ms` on GPU 0 with `warmup=30`, `rep=1000`, exact validation), while `gluon_optimized` measured `0.3482 ms` in the same run.

That SASS note now also captures three follow-on conclusions that matter for future epilogue design. First, the small helper win is consistent with normal `STG.E` scoreboarding: the old helper consumer was not blocked on global completion before executing `SYNCS.ARRIVE`; moving `arrive(empty)` earlier only shortened the local issue window between the barrier and the `STG.E` cluster. Second, helper buffering is not equivalent to simply giving the epilogue more registers, because the helper path transfers ownership into a different partition's registers and therefore offloads the final address-generation and `gl.store` issue stream onto separate warps. Third, a pure source-level rewrite of the current full-fragment schedule to "manually interleave" arithmetic and `STS` is unlikely to buy much, because ptxas already places the SMEM stores early and overlaps them with later fragment arithmetic. The more credible direct-store experiment would need finer ready/store granularity, not just a restated instruction order or a higher epilogue register budget.

The schedule experiment wave is now split cleanly between durable artifacts and live repo code. The full strategy inventory, repeated paired significance analysis, and all alternate schedule harnesses live under `.codex/initiatives/artifacts/ws-block-schedule-exp-2026-04-10/` plus `.codex/initiatives/artifacts/ws-block-scheduling-research-2026-04-10.md`. The only schedule result that survived promotion was the `band_n_20_row_major` traversal, which keeps the inner walk row-major but restricts the live N footprint to 20-column bands. In the artifact-only repeated same-GPU analysis on GPU 0 (`16` rounds, `rep=3000`, alternating order, exact validation), that candidate measured `row_major=0.34270173 ms` versus `band_n_20_row_major=0.34060572 ms`, a mean edge of about `0.61%` with bootstrap 95% CI `[0.00188117, 0.00228858] ms` and sign-test `p=0.000031`.

The live example has since been cleaned back down to only that promoted schedule. `python/examples/gluon/05-moe-bmm1-fused-gather.py` no longer carries the old multi-strategy schedule switch, and the repo-side sweep harness `python/perf/sweep_moe_bmm1_block_schedule.py` has been deleted now that the result is captured in the initiative artifacts. The target bucket improved slightly during that cleanup rather than regressing: the pre-cleanup exact run on GPU 0 was `ws_optimized=0.3419 ms` versus `gluon_optimized=0.3429 ms`, and the post-cleanup rerun came back `ws_optimized=0.3394 ms` versus `gluon_optimized=0.3429 ms` with `warmup=30`, `rep=1000`, exact validation. So the live repo now keeps only the promoted banded traversal, while all exploratory scheduling machinery lives outside `python/`.

The latest structural producer-side experiment changed the live example from two producer partitions (`load_activations` + `load_weights`) to a single shared load partition and ring, matching the higher-level ownership model in `python/perf/matmul_gluon_optimized.py` while keeping the example's helper-wavefront epilogue and exact SwiGLU path. A straight port regressed (`ws_optimized=0.3418 ms`), mostly because the merged loader needed a different register budget and could no longer use the old `x_num_bufs=5, w_num_bufs=4` asymmetric staging. After retuning the merged loader to a shared 4-stage ring with `load_warps=4`, `load_regs=80`, and `mma_regs=20`, the target bucket came back to parity with the pre-merge best: `ws_optimized=0.3394 ms` versus `gluon_optimized=0.3407 ms` on GPU 0 with `warmup=30`, `rep=1000`, exact validation. So the one-load-partition structure is viable in the example, but on this bucket it looks more like a wash than a fresh win.

The latest GPT-OSS low-batch research changed the next implementation priority materially, and that follow-up is now landed. The standalone example now selects a low-batch tile policy dynamically: `slice_size <= 8 -> (block_m=16, row_subtile=2)`, `<= 16 -> (32, 4)`, `<= 32 -> (64, 4)`, and otherwise the old `(128, 8)` path. The important epilogue finding is that `block_m=16` did not require a rewrite; it only required dropping the exact helper-wavefront row-subtile factor from `8` to `2` so the packed split path remained legal. With that policy in place, the example now beats the production reference across the full GPT-OSS 120B MM1 sweep on this machine: `batch=128` `0.03265 ms` vs `0.03304 ms`, `256` `0.03267 ms` vs `0.03351 ms`, `512` `0.03379 ms` vs `0.03415 ms`, `1024` `0.03583 ms` vs `0.03633 ms`, and it stays ahead through `16384` as well. Long-run `rep=3000` confirmation on `128/256/512/1024` kept the same direction. So split-K remains documented, but it is now clearly a deferred design for future workloads rather than the next GPT-OSS step for this example.

One more post-landing sweep pass uncovered a smaller selector bug: the live policy switched from `(64, 4)` to `(128, 8)` too early, which created an avoidable dip around `batch=1280..1536`. Direct same-process A/Bs showed that `block_m=64, row_subtile=4` stays materially better through `slice_size=58` (`batch=1856`) and only loses once `slice_size` reaches `60` (`batch=1920`). Extending that boundary fixed the mid-batch pocket. The refreshed full sweep now has the example ahead of the reference at every GPT-OSS batch point, with the narrowest remaining edge around `batch=3072` and `3584` still positive at about `0.53%` and `0.55%`.

The later merged-loader cleanup is no longer the only viable producer topology. I restored the older separate activation loader plus weight+scale loader on top of the current low-batch selector and helper-wavefront epilogue, then compared it directly against the merged-loader baseline from `9ae413dfa0`. The result is a wash in the broad sense: the split-loader version remains ahead of the reference across the full GPT-OSS sweep and stays in the same overall performance band as the merged-loader version, but the deltas are mixed rather than uniformly positive. On the `rep=1000` sweep it is better through much of the low and mid range (`2048` `0.03986 ms` vs merged `0.04062 ms`, `3072` `0.03986 ms` vs `0.04075 ms`, `7168` `0.05361 ms` vs `0.05568 ms`) and slightly worse in a few higher buckets (`25600` `0.15777 ms` vs `0.15644 ms`, `30720` `0.18300 ms` vs `0.18196 ms`). Direct `rep=3000` A/Bs on representative points showed the same pattern: `7168` favored the split loader by about `3.6%`, while `21504`, `25600`, and `30720` favored the merged loader by about `0.7%`, `1.2%`, and `0.6%` respectively. So the merged single-load topology is not a durable sweep-level performance win by itself; it is mostly a structural simplification.
