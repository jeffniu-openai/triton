## Root Cause
- The bug was not another packet-offset problem.
- For rank-2 `M=64`, `f32`, 4-warp root loads, the handle-aware TMEM memdesc path could satisfy a split-N request with a speculative `I32x32b` candidate before the correct `I16x32bx2` family was considered.
- Two things caused that:
  - `python/src/gluon_ir.cc` treated `I32x32b` and `I16x32bx2` as interchangeable in `matchesDesiredAtom(...)` for rank-2 `M=64` `f32` descriptors.
  - the handle-aware candidate order prefixed row-plan-specific direct layouts ahead of the generic `getTmemCompatibleLayouts(queryTy, numWarps)` order.
- The public descriptor API already knew the correct split-N family for the same root descriptor, so this was a selection bug, not an ISA limitation.

## Structural Fix
- `python/src/gluon_ir.cc`
  - restore strict atom matching for `I32x32b` vs `I16x32bx2`;
  - align handle-aware candidate ranking with `getTmemCompatibleLayouts(queryTy, numWarps)` before appending memdesc-specific rescue layouts; and
  - try the canonical `M=64` split-N TMEM-linear type first in the public descriptor API for the relevant 4-warp `f32` cases.

## Working Principle
- Treat TMEM reinterpret lowering as an exact linear-layout problem, not as a growing list of view-specific rescues.
- The intended durable shape is:
  - derive reinterpret support layouts, origin remaps, row anchors, packet offsets, and atom-family choice from `LinearLayout` compose/invert/pseudoinvert arithmetic;
  - assume there is a sane algebraic lowering for reinterpret/view composition and keep pushing toward it, because once the arithmetic is right the implementation should stop generating whole classes of bugs;
  - expect the arithmetic to be subtle, but treat that as a reason to solve the math cleanly instead of layering more one-off rewrites;
  - delete ad-hoc row/col fixups once the algebraic path exists; and
  - keep clean negatives only where the ISA truly cannot realize the resulting image.

## Linear-Layout Learnings
- The live `block_m_64` reinterpret bug narrowed to a mismatch between two different notions of "packing":
  - memdesc support-query reinterpret was already using exact row-major bit remapping and produced the correct widened sparse support image; but
  - the register side was still being "packed" by hand by deleting a convenient register-col bit.
- That manual register packing is the wrong abstraction boundary. It can preserve enough shape to look plausible while still leaving the sparse-support bit on the wrong input family, which then steers atom selection toward `16x32bx2` instead of the intended packed `32x32b.unpack` path.
- The durable fix direction is:
  - reinterpret the register layout itself with the same exact bit-level row-major arithmetic used for TMEM memdesc reinterpret;
  - compose that reinterpreted register layout with the reinterpreted sparse-support TMEM layout; and
  - only after that derive the direct message family and packet offsets.
- Practical debugging lesson:
  - if a TMEM quotient still carries an unexpected lane/warp basis after a reinterpret, first suspect that one side of the compose was transformed with ad-hoc layout surgery instead of the same reinterpret algebra as the other side.

## 2026-04-10 Merge-Base Audit: hack inventory, remaining reinterpret buckets, and cleanup order

### Scope
- I audited the compiler-side diff against merge-base `7f61ac734edc657b737fb159a1b9d50cb47944e6` (`master`), excluding `.codex`.
- The overall diff is large and much of it is real feature work, but the TMEM debt clusters into a small number of recurring patch families. Those are the ones to keep checking off rather than continuing to accumulate one-off M64 rescues.

### Inventory Of Patchwork / Hack Families

1. Duplicated TMEM ld/st planning across Gluon, verifier, and LLVM lowering
- Current shape:
  - `python/src/gluon_ir.cc`
  - `lib/Dialect/TritonNvidiaGPU/IR/Ops.cpp`
  - `third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/TensorMemoryToLLVM.cpp`
- Smell:
  - the same raw-query / support-query / row-plan ordering decisions are reimplemented in three layers;
  - several fixes in this initiative only worked after making equivalent changes in multiple places;
  - the previous root-load regression existed because the frontend descriptor planner and LLVM-side lowering stopped agreeing on atom-family choice.
- Desired cleanup:
  - one shared TMEM ld/st planner that returns a structural plan:
    - analyzed support layout
    - row-plan / base contract
    - atom family
    - quotient / repetition
    - packet decomposition
  - Gluon, verifier, and LLVM should validate or consume that plan, not recreate it.

2. M64 family selection is still spread across explicit fast paths
- Current shape:
  - `lib/Dialect/TritonNvidiaGPU/IR/Dialect.cpp`
  - `python/src/gluon_ir.cc`
- Smell:
  - `getCanonicalM64SplitNLayout(...)`
  - `getCanonicalContiguousM64Layout(...)`
  - `getDistributedLayoutForTmemLdStLegacyAnchored(...)`
  - stripped-zero-basis retries
  - exact-family probes for legacy-like layouts
- These were useful to recover broken cases quickly, but they are still family-specific routing logic rather than one physical-family model derived from the normalized linear layout.
- Desired cleanup:
  - canonicalize both TMEM-linear and legacy encodings onto one physical-family representation once;
  - derive family choice from that representation and the quotient, not from a growing menu of M64/M128 special entry points.

3. Reinterpret lowering in `TensorMemoryUtils.cpp` still contains packet surgery
- Current shape:
  - `reinterpretLinearLayout(...)`
  - `reinterpretColumnSubviewSupportQueryLayout(...)`
  - packed sparse-support builders
  - `preferPackedI16x32bx2`
  - `legacyLikeColStride`
  - row-zero-lifted guards and direct-view rewrites
  - explicit `packetOffsets` / `secondHalfOffset` rewrites
- Smell:
  - too many places are manually deleting zero bases, shifting packed col bits, or rewriting anchors after the fact;
  - the current implementation is partly algebraic and partly post-hoc surgery.
- Desired cleanup:
  - define reinterpret lowering entirely as:
    1. transform the memdesc view in exact `LinearLayout` space;
    2. transform the register layout through the same reinterpret algebra;
    3. form the quotient in one physical coordinate frame;
    4. factor quotient bits into:
       - message tile
       - packet repetition
       - support-band / subview-selection
       - row-anchor realization
    5. pick the atom family from that factorization.
- Once that exists, the row-zero/M64 packet fixups should collapse away instead of remaining as durable code paths.

4. Legacy TMEM encodings still have a parallel rescue stack
- Current shape:
  - `getDistributedLayoutForTmemLdStLegacyAnchored(...)`
  - `tryLegacyAnchoredExactFamily(...)`
  - `getLegacyLikeColStride()`
- Smell:
  - legacy encodings are repeatedly pattern-matched back into canonical families inside lowering, instead of being canonically normalized once and then lowered through the same planner as TMEM-linear layouts.
- Desired cleanup:
  - build a single legacy-to-canonical physical view bridge up front;
  - after that, the planner should not care whether the source spelling was legacy or TMEM-linear.
- This is directly tied to the live `legacy` `block_m_64` failure.

5. Row-plan propagation is conceptually right but still too ad hoc
- Current shape:
  - explicit `ttng.tmem_ldst_row_plan`
  - `annotateMMAv5TMemOperandRootRowPlan(...)`
  - many `rowPlanOverride` parameters
  - repeated `getTMemLdStRowPlanForQuery(...)` / `getBackingTMemLdStRowPlan(...)` fallback ladders
- Smell:
  - the initiative proved row plans must be explicit producer-owned contracts, but acquisition and projection of that contract are still scattered.
- Desired cleanup:
  - keep row-plan explicitness;
  - move row-plan acquisition and projection into the shared planner;
  - represent overrides as view-projected contracts, not layer-local rescue logic.

6. Some tests still depend on reinterpret as an implicit physical-layout escape hatch
- Highest-signal examples:
  - `python/test/gluon/test_core.py::test_tmem_subslice_block_m_64`
  - `python/test/gluon/test_core.py::test_tmem_subslice_block_m_64_parent_layout`
- Smell:
  - these tests use `_reinterpret(...)` on TMEM slices to reach specific physical subfragments of TMEM by relying on the compiler's current mapping of logical rows/cols onto TMEM rows/cols;
  - that was historically practical before the descriptor view APIs were generalized, but it is not a strong API contract.
- Desired cleanup:
  - understand each test's user intent;
  - rewrite intent tests to use the explicit descriptor/view APIs (`slice/index/reshape/permute`) that now carry real guarantees;
  - keep only narrow reinterpret smoke tests for what reinterpret itself actually promises.

  - derive packet decomposition from the quotient itself and explicitly separate support-band bits from repetition bits;

    - plain logical slices do not restate the old borrowed-physical-fragment
      intent; they preserve the same problematic M64 mapping
- Experiment 2: explicit quarter-band reorder
  - candidate view:
    - `reshape((64, 2, 2, 32)).permute((0, 2, 1, 3)).reshape((64, 4, 32))`
  - rationale:
    - this reorders quarter bands from `[0, 1, 2, 3]` to `[0, 2, 1, 3]`,
      which matches the old `block_m_64` expected borrowed-half-band layout
      much better than plain slices do
  - result:
    - direct stores into the reordered band views fail cleanly during parsing
      with:
      - `unsupported tensor memory descriptor view for direct tcgen05.ld/st`
      - `required row anchors 32,64 are not directly representable in the descriptor view`
    - a broader rank-3 version of the same idea also exposed a
      `getDistributedLayoutForTmemLdSt(...)` assertion on `dims.size() == 2`
      when asking `get_reg_layout()` on the intermediate parent view
  - conclusion:
    - the reordered view is a plausible explicit-contract target, but it is not
      directly lowerable today; the next step is either one more explicit view
      projection or a compiler-side fix for reordered M64 quarter-band views
- Follow-up probe: split rows first, then reorder quarter bands
  - idea:
    - reshape to `2 x 32 x 2 x 2 x 32`, permute the quarter-band dimensions,
      then index each `32`-row half so the final stores only need the already
      supported `32`-row direct frontier
  - throwaway probes:
    - `/tmp/probe_blockm64_reorder_rowsplit.py`
    - `/tmp/probe_blockm64_reorder_rowsplit2.py`
  - result:
    - the looped version hit a Gluon frontend limitation (`'List' object has no
      attribute 'func'`) because Python list iteration in a JIT kernel is not
      supported there
    - the unrolled version got farther but failed at the explicit TMEM view
      level:
      - `failed to infer memdesc_index result type`
      - `unsupported tensor memory memdesc_subslice view; preserved tensor memory view encoding also failed: rank must be less than or equal to the memdesc rank for tensor memory`
  - conclusion:
    - even if the row-split idea is algebraically right, the current explicit
      view path also appears blocked by higher-rank TMEM view/index inference,
      not only by the final ld/st planner
- Durable takeaway:
  - the failed rewrites are no longer just "tests I haven't finished rewriting"
  - they now identify concrete missing TMEM feature/surface-coverage buckets:
    - reordered M64 quarter-band explicit views are not directly lowerable
      today because of row-anchor materialization gaps; and
    - the higher-rank row-split workaround is not yet fully representable by
      current TMEM reshape/index/subslice inference
- Future sessions should remember this when returning to the bug/hack backlog:

    contract is actually expressible.
