## Important What-We-Learned

### 1. One real root cause was already fixed
There was a real Gluon/LLVM divergence for `M=64` direct TMEM ld/st:
- Gluon handle-aware layout selection preferred query-type/split-N layouts
- LLVM lowering still tried raw-query first

That divergence has already been fixed in the dirty tree by:
- preferring query-type lowering before raw-query for rank-2, `f32`, `M=64`, 4-warp TMEM loads in `TensorMemoryToLLVM.cpp`

What that fix proved:
- direct `64x32` TMEM roundtrip regressions were real and are now fixed in the dirty tree
- the remaining MMA bug is not the same issue

### 2. The direct roundtrip regression is gone
This previously failing test is green in the dirty tree:
- `python/test/gluon/test_core.py::test_tmem_linear_roundtrip_splitn_shapes[linear_m64_splitn_64x32-layout11-64-32-expected_offset_imms11]`

The key observation from manual PTX probing:
- direct roundtrip on `_make_tmem_linear_layout_m64(32)` now emits `16x32bx2.x8` with immediate `8`
- numerics are correct for both `instr_variant='16x32bx2'` and `instr_variant='32x32b_splitn'`

### 3. The remaining MMA bug is now narrower and more structural
The remaining failing MMA load is no longer winning through the old raw-query path.

Latest trace result:
- `TRITON_TRACE_TMEM_QUERY_LOWERING_FILE=1` on the exact failing node shows the first successful candidate is:
  - `queryType 64x32 ok atom=0 regsPerMsg=1 baseOffset=0 warpBase0=2097152 warpBase1=4194304 ...`
- `atom=0` here is `I32x32b`

Interpretation:
- LLVM is now taking a query-type path
- but the winning query-type candidate is still a scalarized `I32x32b` lowering for the root accumulator readback
- that candidate is wrong for this kernel

### 4. The public descriptor API already knows a better family
For a root descriptor equivalent to `TensorMemoryLayout((64, 32), col_stride=1)`:
- `tensor_memory_descriptor_type(...).get_reg_layout(num_warps=4, instr_variant=auto/32x32b/32x32b_splitn/16x32bx2)` returns the split-N-style register layout with:
  - `reg [[0,1],[0,2],[0,4],[0,16]]`
  - `lane [[1,0],[2,0],[4,0],[8,0],[0,8]]`
  - `warp [[16,0],[32,0]]`

That means the remaining issue is probably not that the descriptor family is intrinsically unsupported. It is more likely that:
- the chosen result layout for `acc_tmem.load()` is being validated against the wrong candidate family, or
- the lowering auto-atom heuristic still prefers `I32x32b` for an `M64` split-N-style quotient that should lower through `I16x32bx2`

### `python/src/gluon_ir.cc`

- that may be useful for selecting a layout family, but it may also hide the fact that the chosen layout is only correct for one of the two atoms

## Current Working Hypothesis
The core issue is likely not packet offsets or warp-base arithmetic by themselves.

The more plausible structural bug is:
- for rank-2 `M=64`, `f32`, 4-warp root loads, the auto/query-type lowering heuristic is still allowed to accept an `I32x32b` encoding too early
- but some of those layouts are only semantically correct when realized through the split-N `I16x32bx2` family
- later basis/offset repair code is trying to compensate for this wrong family choice and cannot do so reliably

If that hypothesis is right, the correct fix is:
- encode the M64 split-N family preference at the linear-layout/encoding-selection layer
- ensure `computeTMemLdStEncodingInfo(...)` or its callers prefer the correct atom family for those layouts
- then delete the temporary root-M64 raw-query override/debug paths and any now-obsolete M64 basis surgery
