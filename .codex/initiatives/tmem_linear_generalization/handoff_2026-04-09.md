## Root Cause
- The bug was not another packet-offset problem.
- For rank-2 `M=64`, `f32`, 4-warp root loads, the handle-aware TMEM memdesc path could satisfy a split-N request with a speculative `I32x32b` candidate before the correct `I16x32bx2` family was considered.
- Two things caused that:
  - `python/src/gluon_ir.cc` treated `I32x32b` and `I16x32bx2` as interchangeable in `matchesDesiredAtom(...)` for rank-2 `M=64` `f32` descriptors.
  - the handle-aware candidate order prefixed row-plan-specific direct layouts ahead of the generic `getTmemCompatibleLayouts(queryTy, numWarps)` order.
- The public descriptor API already knew the correct split-N family for the same root descriptor, so this was a selection bug, not an ISA limitation.

## Structural Fix
- `python/src/gluon_ir.cc`
  - restore strict atom matching for `I32x32b` vs `I16x32bx2`;
  - align handle-aware candidate ranking with `getTmemCompatibleLayouts(queryTy, numWarps)` before appending memdesc-specific rescue layouts; and
  - try the canonical `M=64` split-N TMEM-linear type first in the public descriptor API for the relevant 4-warp `f32` cases.
- `lib/Dialect/TritonNvidiaGPU/IR/Dialect.cpp`
  - factor a reusable canonical `M=64` split-N linear layout builder; and
  - inject that canonical split-N layout into direct-layout construction and compatible-layout enumeration.
- `third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/TensorMemoryToLLVM.cpp`
  - keep query-type lowering ahead of raw-query for the same `M=64` root-load family so LLVM follows the same structural choice as Gluon.
- `lib/Dialect/TritonNvidiaGPU/IR/TensorMemoryUtils.cpp`
  - keep the earlier validated row-anchor/direct-view fixes that were already supporting the broader row/col runtime frontier.

## Working Principle
- Treat TMEM reinterpret lowering as an exact linear-layout problem, not as a growing list of view-specific rescues.
- The intended durable shape is:
  - derive reinterpret support layouts, origin remaps, row anchors, packet offsets, and atom-family choice from `LinearLayout` compose/invert/pseudoinvert arithmetic;
  - assume there is a sane algebraic lowering for reinterpret/view composition and keep pushing toward it, because once the arithmetic is right the implementation should stop generating whole classes of bugs;
  - expect the arithmetic to be subtle, but treat that as a reason to solve the math cleanly instead of layering more one-off rewrites;
  - delete ad-hoc row/col fixups once the algebraic path exists; and
  - keep clean negatives only where the ISA truly cannot realize the resulting image.

## Linear-Layout Learnings
- The live `block_m_64` reinterpret bug narrowed to a mismatch between two different notions of "packing":
  - memdesc support-query reinterpret was already using exact row-major bit remapping and produced the correct widened sparse support image; but
  - the register side was still being "packed" by hand by deleting a convenient register-col bit.
- That manual register packing is the wrong abstraction boundary. It can preserve enough shape to look plausible while still leaving the sparse-support bit on the wrong input family, which then steers atom selection toward `16x32bx2` instead of the intended packed `32x32b.unpack` path.
- The durable fix direction is:
  - reinterpret the register layout itself with the same exact bit-level row-major arithmetic used for TMEM memdesc reinterpret;
  - compose that reinterpreted register layout with the reinterpreted sparse-support TMEM layout; and
  - only after that derive the direct message family and packet offsets.
- Practical debugging lesson:
  - if a TMEM quotient still carries an unexpected lane/warp basis after a reinterpret, first suspect that one side of the compose was transformed with ad-hoc layout surgery instead of the same reinterpret algebra as the other side.

  - the initiative already showed that packet/anchor bugs can look like random runtime faults (`misaligned address`) until the quotient/anchor arithmetic is corrected.
  - Lesson: correct linear-layout factoring beats hand-tuned anchor nudges.

### What To Rewrite In Tests

1. Rewrite the `block_m_64` intent tests away from implicit reinterpret mapping
- `test_tmem_subslice_block_m_64`
  - keep the intent:
    - update one physical half-band of the M64 TMEM tile;
    - update three small physical subfragments;
  - rewrite the kernel using explicit descriptor/view composition that names those physical bands through `reshape/permute/slice/index`, then only use `_reinterpret` where the API contract genuinely requires bitcast semantics.

2. Rewrite the parent-layout test into either a guaranteed-view test or a narrow reinterpret smoke test
- `test_tmem_subslice_block_m_64_parent_layout`
  - if the intent is "a user should be able to target this physical subview with guaranteed APIs", rewrite it to those APIs and keep it positive;
  - if the intent is only "the current implicit parent-layout reinterpret happened to work before", do not keep that as a hard semantic contract after changing TMEM lowering.

3. Keep one small reinterpret-specific test surface
- It should check only what reinterpret itself guarantees:
  - bitcount / view preservation
  - legality diagnostics
  - no crashes
  - direct lowering only when the resulting physical support image is actually materializable by the ISA.

### Cleanup Order

1. Unify the TMEM ld/st planner
- Build one shared plan object consumed by Gluon, verifier, and LLVM lowering.

2. Remove the legacy-vs-linear divergence
- Canonicalize legacy physical families once and lower them through the same support/query planner as TMEM-linear layouts.
- This is the next direct code target because it should close `test_tmem_subslice_block_m_64[legacy]`.

3. Replace packet surgery with quotient factorization
- For reinterpret/support queries, derive packet offsets / repetition / support-band selection directly from the quotient in one physical coordinate frame.
- This is the next target after legacy unification and should close the parent-layout bucket cleanly.

4. Rewrite the reinterpret-UB tests to explicit descriptor/view APIs
- Do this once the core logic is stable enough that the rewritten tests can reflect the intended API contract instead of the old compiler accident.

5. Then re-broaden validation
- nearest `block_m_64` tests
- TMEM runtime matrix
- matmul / MMA
- `triton_kernels` matmul
- broader suite
