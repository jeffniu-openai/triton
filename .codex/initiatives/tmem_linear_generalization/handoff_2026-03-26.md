## Landed Compiler Changes

### 1. TMEM memdesc inference moved to op-level inference
This is the big structural change the user requested.

Files:
- `include/triton/Dialect/Triton/IR/Dialect.h`
- `lib/Dialect/TritonGPU/IR/Dialect.cpp`
- `lib/Dialect/Gluon/IR/Dialect.cpp`
- `lib/Dialect/TritonNvidiaGPU/IR/Dialect.cpp`
- `include/triton/Dialect/TritonGPU/IR/TritonGPUOps.td`
- `lib/Dialect/TritonGPU/IR/Ops.cpp`
- `python/src/gluon_ir.cc`

What changed:
- Added a TMEM-aware memdesc reinterpret/subslice/index/reshape inference path through dialect interfaces and `InferTypeOpInterface`.
- `gluon_ir.cc` is now mostly a thin wrapper around checked op builders; it no longer performs bespoke TMEM view/type inference itself.
- The checked-builder route is important because inference can fail and must return a clean error instead of asserting.

Relevant interfaces / ops:
- `DialectInferLayoutInterface` now has TMEM-aware hooks used by TTG/TTNG/Gluon.
- `TTG_MemDescSubsliceOp`, `TTG_MemDescReshapeOp`, and `TTG_MemDescReinterpretOp` infer result types instead of forcing Python to construct them manually.

### 2. TMEM canonicalization centralized
Files:
- `include/triton/Dialect/TritonNvidiaGPU/IR/Dialect.h`
- `lib/Dialect/TritonNvidiaGPU/IR/Dialect.cpp`

Key helper:
- `getCanonicalTMemLinearEncoding(...)`

What changed:
- Legacy TMEM sugar remains accepted at the source/IR boundary.
- Consumers/analyzers canonicalize to `tensor_memory_linear` before reasoning about legality or view semantics.
- `gluon_ir.cc` now calls the centralized helper rather than reconstructing canonical TMEM layouts itself.

### 3. TMEM view inference centralized in TensorMemoryUtils
File:
- `lib/Dialect/TritonNvidiaGPU/IR/TensorMemoryUtils.cpp`

Important helpers:
- `getTMemViewAnalysisLayout(...)`
- `tryMakeTMemViewEncoding(...)`
- `inferTMemReshapeOpEncoding(...)`
- `inferTMemIndexOpEncoding(...)`
- `inferTMemSubsliceOpEncoding(...)`
- `canUseTMemViewEncoding(...)`

Important fixes already landed:
- `getTMemViewAnalysisLayout(...)` canonicalizes using `shape.take_back(layoutRank)`.
- `canUseTMemViewEncoding(...)` revalidates non-scales TMEM encodings against the suffix shape before reusing them.

These changes fixed a real regression in higher-rank lifted TMEM view handling.

### 4. Shared linear-layout utilities are now reused
Previously-identified duplication around linear-layout parsing / printing / basis/order extraction has been cleaned up.

Current state:
- `lib/Dialect/TritonNvidiaGPU/IR/Dialect.cpp` calls:
  - `triton::gpu::printLinearLayout(...)`
  - `triton::gpu::parseLinearLayout(...)`
  - `::mlir::triton::basesPerDimImpl(...)`
  - `::mlir::triton::orderPerDimImpl(...)`
- The NVIDIA dialect is no longer carrying a separate parse/print implementation.

### 5. Strict explicit-layout policy for plain TMEM ld/st/alloc
Files:
- `lib/Dialect/TritonNvidiaGPU/IR/Ops.cpp`
- `third_party/nvidia/backend/compiler.py`

Current policy:
- Plain `ttng.tmem_load`, `ttng.tmem_store`, and initialized `ttng.tmem_alloc` reject explicit register layouts that are not directly TMEM-compatible.
- The old late backend `relayout-tritongpu` scheduling for non-WS kernels was removed.
- Do not reintroduce implicit `convert_layout` repair for these ops.

## Open Problems / Known BUG Buckets

### 1. Multidimensional TMEM slice/view miscompiles
This is the main remaining correctness gap.

Symptoms:
- Higher-rank `memdesc_subslice` / `memdesc_index` chains can compile but write to the wrong physical TMEM columns.
- Direct multidimensional slice views on some lifted layouts can compile but update the wrong region.
- Some two-CTA MMAv5 higher-rank view chains still fail cleanly during inference with CGA mismatch diagnostics; those are currently treated as unsupported boundaries.

Tests / BUG markers:
- `python/test/gluon/test_tmem_runtime_matrix.py:2006`
- `python/test/gluon/test_tmem_runtime_matrix.py:2068`
- `python/test/gluon/test_tmem_runtime_matrix.py:2155`

Current BUG texts:
- `BUG: higher-rank multidimensional TMEM slices compile but write incorrect values`
- `BUG: two-CTA higher-rank multidimensional TMEM slices compile but write incorrect values`
- `BUG: direct multidimensional TMEM slice on layout '{layout_name}' compiles but writes incorrect values`

Relevant implementation file:
- `lib/Dialect/TritonNvidiaGPU/IR/TensorMemoryUtils.cpp`

Likely investigation area:
- the mapping from generic logical offsets / subslices / index chains back to legal physical TMEM row/col[/block] coordinates
- suffix-shape handling and derived-view encoding reuse

### 2. `tcgen05.copy.warpx2` remains unsupported
Status:
- Intentionally clean-unsupported.
- Direct PTX probing showed this is not just an opcode-selection gap.
- The inherited `warpx4` descriptor/message schedule does not correctly model `warpx2`.
- Intermediate TMEM destination deltas `+1` and `+2` fault with misaligned-address errors.
- Enabling it will need a copy-family-specific descriptor/address/message planner, not just classifier widening.

Important files / tests:
- `lib/Dialect/TritonNvidiaGPU/IR/Ops.cpp`
- `third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/TensorMemoryToLLVM.cpp`
- `python/test/gluon/test_tmem_runtime_matrix.py`
- experiments under `.codex/initiatives/tmem_linear_generalization/experiments/`

Useful test names:
